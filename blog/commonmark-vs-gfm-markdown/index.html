CommonMark vs GFM: What Changes?

A preview works in one place and breaks in another. Find out whether the cause is core Markdown syntax, a GFM extension, or a renderer-specific setting.

If Markdown looks different between tools, the source may be valid in both. Markdown is interpreted by a renderer. CommonMark defines a core syntax; GitHub Flavored Markdown (GFM) builds on CommonMark and adds specific extensions. A third product can support only part of either set, or apply its own settings.

Why output differs between a preview and GitHub

Start by separating three questions: does the syntax belong to the specification you expect, does the destination implement that feature, and are renderer options changing the result? A local preview demonstrates that preview's behavior; it cannot guarantee another site or export will match.

CommonMark and GFM at a glance

Syntax or behaviorCommonMark coreGFM specification
Headings, paragraphs, emphasis, links, lists, blockquotes and fenced codeYesYes
Pipe tablesNoExtension
Task-list markers such as - [ ]NoExtension
Strikethrough such as ~~text~~NoExtension
Bare-URL autolinkingNot part of the core syntaxExtension
Math, Mermaid diagrams, and alert calloutsNoNot defined by the GFM specification

GFM documents extensions such as tables, task-list items, strikethrough, and autolinks. Math and diagram fences need additional renderer support. A platform may add more features of its own, so “supports Markdown” is not a complete compatibility statement.

Debug a mismatch with a small test

  1. Copy the smallest source sample that shows the problem. Remove private or unrelated document text.
  2. Record the destination, its Markdown flavor if documented, and any relevant option or plugin.
  3. Compare one feature at a time: a table, task list, autolink, or line break.
  4. Inspect the saved file and final destination separately from the live preview.
  5. Keep the original Markdown so you can switch renderers without losing source structure.

Line breaks are a common false alarm: CommonMark treats an ordinary newline inside a paragraph as a soft break. A renderer may output that as a space or line ending; a blank line starts a new paragraph, while two trailing spaces or a backslash before the newline create a hard break. Some renderers also offer an option that turns soft breaks into hard breaks.

Keep the document portable

  • Use core syntax when the same source must render in many destinations.
  • When using GFM-only features, label the requirement and preview the target platform.
  • Keep essential instructions in prose instead of relying on a table or checkbox alone.
  • Check links and relative image paths after moving the Markdown file.
  • Inspect each export format independently; a browser preview does not validate a PDF or another application's renderer.

For a quick compatibility check, paste the examples into the Markups preview, then test the same source in its intended destination. Markups is one renderer in that comparison, not a guarantee that every destination behaves the same.
